RadioZapper Memory Management

This document describes RadioZapper’s fixed-size, generational-handle memory pool system.

Where the code lives now

The memory system is split into two layers:

  1. Generic pool library: src/utils/memory_pool.h

    • Template-based pool: MemoryPool<T, PoolSize, Traits>
    • Generic RAII guard: MemoryPoolGuard<Pool>
    • No Zephyr includes; time is provided via Traits::now().

  2. Packet-specific adapter: src/mesh/packet_pool.h + src/mesh/packet_pool.cpp

    • PacketPool is a thin typedef/adapter on top of MemoryPool<ManagedPacket, PACKET_POOL_SIZE, ManagedPacketPoolTraits>.
    • ManagedPacketPoolTraits wires in Zephyr-specific initialization (k_work_init_delayable) and a Zephyr clock (k_uptime_get()).
    • packet_pool.cpp owns the Zephyr logging module registration (LOG_MODULE_REGISTER(packet_pool, ...)) and implements packet-only helpers.

This split is intentional: memory_pool.h is the piece you can peel off into a separate MIT-licensed library without pulling in RadioZapper/Zephyr packet details.

Why not new / delete?

Dynamic allocation is a poor fit for this codebase because:

  • Embedded memory is limited and fragmentation is a real risk.
  • The send/ACK/retry pipeline is asynchronous; it’s easier to reason about lifetime with a fixed pool and handles.

Why not just a free list?

A free list is simple but has some downsides:

  • Use-after-free risks: If you free an item and then accidentally use the old pointer, you might corrupt memory or cause undefined behavior.
  • ABA problems: If you free an item and then allocate a new one in the same slot, old handles might still appear valid but point to the wrong object.

Why generational handles?

Generational handles help mitigate use-after-free and ABA issues by encoding a generation counter in the handle. Each time a slot is allocated, its generation is incremented. This way, if you free a slot and then allocate a new one in the same slot, old handles will fail the generation check.

Goals and design constraints

The design is inspired by Rust-like “ownership/borrowing” ideas, but implemented as runtime checks:

  1. Fixed-size pool for predictable memory usage.

  2. Generational handles to reduce use-after-free/ABA issues.

  3. Exclusive access via a lock flag to discourage concurrent mutation.

  4. Debuggable lock ownership via a per-slot locked_by tag.

Optional thread safety

By default, src/utils/memory_pool.h is not thread-safe: it uses a simple per-slot is_locked flag and expects either cooperative/single-thread usage or external synchronization.

If you compile with MEMORY_POOL_THREAD_SAFE (e.g. -DMEMORY_POOL_THREAD_SAFE), MemoryPool switches to a Zephyr-backed implementation that wraps its internal bookkeeping with a k_mutex.

What this changes:

  • init(), alloc(), acquire(), release(), and free() take a mutex while they read/modify pool metadata (in_use, generation, is_locked, last_touched_time).
  • The check-and-set of is_locked becomes safe across threads.

What this does not change:

  • The returned T* from acquire() is still only protected by the pool’s logical exclusivity (is_locked). The global mutex is not held while you use the pointer; it only protects the pool’s metadata transitions.
  • You still must follow the “acquire → use → release/free” discipline.

Tradeoff / library extraction note:

  • With MEMORY_POOL_THREAD_SAFE enabled, memory_pool.h includes Zephyr (<zephyr/kernel.h>). When porting to a new platform, it may be worth leaving it as non-thread-safe for the initial port, and then adding a thread-safe wrapper.

API overview

MemoryPool<T, PoolSize, Traits> (generic)

Key operations:

  • init()
    • Initializes every slot and calls Traits::init(T&) once per slot.
  • alloc() -> uint16_t
    • Marks a free slot as in-use, bumps the generation, calls Traits::on_alloc(T&), and returns a 16-bit handle.
    • Returns 0xFFFF (INVALID_HANDLE) if the pool is full.
  • acquire(handle) -> T*
    • Returns a pointer only if:
      • slot is in use
      • generation matches
      • slot is not currently locked
    • Locks the slot on success.
    • The slot metadata also records a locked_by tag for debugging.
  • release(handle)
    • Unlocks the slot (does not free it).
  • free(handle)
    • Returns the slot to the pool.
    • Requires the slot is currently locked by the caller (i.e., acquired).

Optional debug helpers:

  • acquire_with_owner(handle, owner_tag) -> T*
    • Same as acquire(), but stamps locked_by = owner_tag when the lock is taken.
    • Owner tag is a uint32_t that can be used to identify which subsystem or code path currently owns the lock. You are intended to use it by having an ENUM for each function that may touch the pool, and passing static_cast<uint32_t>(MyEnum::X) as the owner tag.
  • locked_by(handle) -> uint32_t
    • Returns the most recently stamped owner tag for that slot (or 0 if invalid / not in use).

Traits hooks:

  • Traits::init(T&) — run once at MemoryPool::init() time
  • Traits::on_alloc(T&) — run on each allocation
  • Traits::now() -> int64_t — used for last_touched_time bookkeeping (default is 0)

Handles (generic)

The handle returned by alloc() is a 16-bit value encoding:

15       8 7        0
+---------+---------+
|  Index  |   Gen   |
+---------+---------+
  • Index is 8-bit, so the pool size is limited to 255 slots.
  • Generation increments each time a slot is allocated.

This means old handles fail cleanly after a free/reuse:

  • If the slot was freed: in_use is false.
  • If the slot was freed and reallocated: generation mismatch.

MemoryPoolGuard<Pool> (generic)

MemoryPoolGuard is a small helper around a handle:

  • acquire() tries to lock the slot and caches a T*.
  • acquire(owner_tag) does the same, but stamps locked_by for debugging.
  • operator->() gives access to the object once acquired.
  • release() unlocks the slot but keeps the handle.
  • free_item() frees the slot back to the pool (and releases the cached pointer).

Recommended locked_by representation:

  • Prefer an enum-backed integer tag (e.g. enum class PoolOwner : uint32_t) and pass static_cast<uint32_t>(PoolOwner::X).
  • Avoid short char arrays inside each slot: they bloat the pool (one array per slot) and are awkward to manage safely on embedded targets.

Destructor behavior:

  • If the guard is currently holding the object pointer (i.e. acquired), the destructor releases the lock.
  • The destructor does not free the slot.

This “release-on-destruction but not free” rule matches how packets are passed between layers (ownership transfer).

Packet layer (PacketPool / PacketGuard)

PacketPool and PacketGuard preserve the existing call-site API, but are now implemented using the generic pool.

What’s packet-specific:

  • Slot initialization: ManagedPacketPoolTraits::init() initializes Zephyr work items inside each ManagedPacket:
    • ack_timeout_work uses ack_timeout_handler
    • send_work uses tx_work_handler
  • Packet helper: PacketPool::get_handle_for_packet_with_packet_id(packet_id) scans the pool for a matching ManagedPacket::id and returns its handle (or 0xFFFF).
  • Logging: packet_pool.cpp registers the packet_pool log module. The header intentionally does not declare/register a log module to avoid Zephyr’s __log_level redefinition errors.

Back-compat functions exist for legacy call sites:

  • PacketPool::_acquire(handle)
  • PacketPool::_release(handle)
  • PacketPool::_free(handle)
